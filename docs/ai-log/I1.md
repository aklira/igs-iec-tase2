# I1 — The third-party peer of the interop bench (build)

## Prompt

Prepare the interop bench with a licensed third-party TASE.2 implementation, as a separate process and a black box. The maintainer
authorised, for the build only, a minimal correction of the peer's sources (decision D-068).

## Summary

- `bench/third-party-peer/build.sh`: extracts the peer's archive outside the repository, builds its example programs in a container,
  and copies them to a directory outside the repository. Its paths come from environment variables, and its optional patch is applied in
  the container.
- Two build defects were corrected by a patch kept outside the repository (D-068): two conditional statements wrapped in braces.
  The debug option of the peer is left at its default. The example programs build.
- The programs run as separate processes. Nothing of the peer is in the repository.

## Not done

- The bench service, the configuration of the peer's objects, and the scenarios in both directions: they need the peer's
  documentation, and the decision of the maintainer on the scope of the reading (D-068 covers the build only).

## Status of the peer in the bench

- A small server program of the peer's public API is built outside the repository, with the same build as the peer's library, and it
  starts. The bench has a service for it (`peer-third-party`, address 172.31.110.13, its binary in `bench/third-party-peer/bin`,
  ignored by git). Its program is not in the repository.
- Association: not established. The bench's client of this repository gets a lost connection. The peer's own client example, run against
  the same program, connects over TCP, then receives a connection request where it expects a confirmation, and its association fails.
  The address-matching rule of the peer was changed to the AP-title only, without effect. The cause is not known: it is in the peer's
  connection layer or in its build, not in this repository's stack.
- Next step: ask the peer's vendor for a working build, under the maintenance agreement (article 2 of the support contract).

## Findings of the second diagnosis

- Captured on the wire, the association of the peer's own client example with the peer's server example succeeds. Its connection request
  carries the transport selectors 0001 (calling and called). Our client sent none by default: a first cause, now selectable with the
  command line's `--calling-tsap` and `--called-tsap` options.
- With those selectors, our client receives the peer's connection confirmation, then its association request is refused: the request
  proposes the current MMS application context (1.0.9506.2.5), while the peer's client proposes the 2002 context (1.0.9506.2.3). The
  stack's initiator proposes only the current context (decision D-027); the server side of the stack accepts both.
- Next decision: whether the stack's initiator may propose the 2002 context, as an option, for the interoperability of the bench. This
  is a change of the MMS repository (its own plan), which the maintainer decides.

## Result: the client reads a point of the peer's example server

- With the transport selectors, the 2002 application context, the called AP-title and the AE-qualifiers of the peer's example configuration,
  the client of this repository associates with the example server and reads a point. The values of the peer's example configuration
  (its domain and its table identifier) are read from the environment of the bench, and are not in the repository.
- The bench test `test_i1_third_party_peer.py` runs this read; it is skipped when the environment does not give the values.
- Changes of this repository for it: the command-line options of the transport selectors, the 2002 context, the called AP-title and the
  AE-qualifiers; in the MMS repository, the initiator's options for the same fields (its changelog and tests).

## Result: the example client of the peer associates with our server

- Our server, configured for the example client (its configuration is in the git-ignored directory of the bench), accepts its
  association, and the client reports it connected. Its first requests get answers. Its later requests name objects that our
  configuration does not hold, and they fail: this is configuration, not a protocol difference. The test checks the association only.
- The bench gains the example client (service `peer-client-example`), the server service `device-interop`, and the reverse test in
  `test_i1_third_party_peer.py`. Both directions pass with the peer's values, read from the environment.
