# B2 — Association

## Prompt

Run task B2 of `IMPLEMENTATION.md`: the sans-I/O association logic: what is read and checked after the MMS Initiate, in both
roles. Read IEC 60870-6-503 §6 and §7. Done when there are tests for a matching and a mismatching table.

## Summary

- **Client**: `client_after_initiate` in `crates/igs-iec-tase2-link/src/association.rs`. It takes the three variables read after
  the Initiate (`Bilateral_Table_ID`, `TASE.2_Version`, `Supported_Features`), compares the table identifier, then the
  TASE.2 version, and returns the established association with the features, or the conflict (D-030).
- **Server**: `server_on_initiate`. The server refuses with an Initiate-ErrorPDU (OTHER) when it is the designated initiator
  of the peer; otherwise the Bilateral Table admits the client, and a refusal is a negative response (D-031).
- **Release**: `release` disables the active transfer sets and deselects the selected devices, for a Conclude or an Abort
  (D-032).
- **Version conversion**: `Tase2Version::from_mms` reads the model's `TASE.2Version` into the link's version type
  (`version.rs`).
- **Decisions**: D-030, D-031, D-032.
- **Tests**: `tests/association.rs`, 11 tests: the matching table and version; a mismatching table identifier, alone and with
  a mismatching version; a mismatching TASE.2 version; the acceptance and each refusal; the release and its repetition.
- **Gate**: `cargo fmt --all --check`, clippy with `-D warnings`, the workspace tests with all features, `cargo deny check`,
  and `codegen --check`, all green.

## Found on the way

- A TASE.2 version outside 16 bits cannot reach the link: the model refuses such an integer when it reads it. The test that
  expected a refusal was replaced by one that checks the conversion of a valid version.
- The initiator role is not an attribute of the Bilateral Table object model; it is kept in a `ServerPolicy` (D-031).
