# S3 — Server interop and load

## Prompt

Run task S3 of `IMPLEMENTATION.md`: the bench scenarios of the server, and a load test with 10 000 points and several
associations, latencies measured, and the gaps recorded (rule 10).

## Summary

- **Driver**: `crates/igstase2-load/`, the binary `igstase2-load`. It runs `--clients` associations (1 to 256) at once against a
  server (`--server ADDR`) or against one in process (`--local`), reads every point in chunks, writes a few points, measures the
  latency of each operation, and counts the errors and the reports that reach an association which did not start a transfer
  set. It exits 1 when a counter is not 0, or when a local run measures no report.
- **Configuration**: `bench/device/gen_load_config.py` writes `bench/device/load-10k.toml` (10 000 points, the same table as the
  local run). The file is generated and git ignores it.
- **Bench**: the compose service `device-load` (the server of 10 000 points, `172.31.110.12`) and the driver mounted in
  `client-tase2`. `bench/device/build-tase2.sh` builds the driver with the other two binaries.
- **Scenarios**: `bench/tests/test_s3_load.py`, 2 tests: the load run (10 000 points, 8 associations: zero error, zero stray
  report, 800 reads as the workload implies) and the refusal when no server answers.
- **Server test**: `a_report_reaches_only_the_association_that_started_its_transfer_set` (`crates/igs-iec-tase2/tests/server.rs`):
  two associations at once, only the first holds the transfer set, and only the first receives the report.
- **Run**: both bench tests pass. The transcript is `bench/transcripts/S3-run.txt`. The figures and the gaps are in
  `docs/load-test.md`: associate p50 8.7 ms, read p50 8.8 ms (p99 11.4 ms), write p50 8.4 ms, for 8 associations on 10 000 points.
- **Decision**: D-058 in `PROVENANCE.md`.

## Found on the way

- A `kill -INT` to a server started in the background of a non-interactive shell does not stop it: the shell ignores SIGINT for
  background jobs. The server was stopped with `kill`. The driver itself does not depend on this.
- The `.gitignore` of the device first gained a duplicate `bin/` line; it was reduced to the new `load-10k.toml` line.
- The matrix of the server had no test of two associations at once. The load run needs one, because the isolation of the reports
  is what a load on several associations can break. The test was added to the server's tests before the bench run.

## Not done

- **Report latency over the bench.** It is measured in process only (`--local`); the bench starts no transfer set, so it measures
  none. Recorded as a gap in `docs/load-test.md`.
- **Repeated runs.** One bench run of a few seconds; no variance, no soak test, no memory over time.
- **Third-party peer.** The reference peer does not serve TASE.2 (D-010), so there is no interop with a foreign server or client.
- **Critical acknowledgement, blocked reports, dual use** are not exercised under load (D-046, D-054).
