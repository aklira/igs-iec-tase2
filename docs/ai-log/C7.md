# C7 — Server: the devices, the information messages, the block-2 conditions

## Prompt

Run task C7 of `IMPLEMENTATION.md`: the server side of blocks 2, 4 and 5, under the table of each client, with a simulated control point
for the demonstration; the demonstration file names one control point.

## Summary

- **Devices** (`crates/igs-iec-tase2/src/server.rs`): `DeviceConfig` in the server configuration. A Select reads `<name>_SBO` and arms the
  device (the link's `Device`), an Operate writes the command (simulated: it completes at once), Get Tag and Set Tag use `<name>_TAG`. The
  table's device access (`DeviceAccess`) gives the permissions, the CheckBackID and the timeout.
- **Information messages**: the client writes `IM_Transfer_Set` (AA-specific) to start and stop it, per association; `TaseServer::send_information`
  gives a message to each enabled association, reported as an Information Report of the header and the buffer.
- **Block 2**: already served (C5), with no change.
- **Configuration** (`crates/igstase2-server`): `[[device]]` (`domain`, `name`, `class` = `sbo` | `non-sbo`, `closing_commands`), and the table
  access kind `device` with `check_back_id` and `timeout_s`. The demonstration file `bench/device/tase2-demo.toml` names one control point:
  `Breaker12`, an SBO device whose command 2 closes it. The file loads (the server serves after three seconds).
- **Tests**: ten new tests in `crates/igs-iec-tase2/tests/server.rs`, through the client over MMS; two configuration tests in `igstase2-server`.
  All 30 tests of the server file pass; the full gate is green.
- **Decision**: D-066 (the simulated commands, the timeout as the only release, the information messages per association).

## Found on the way

- A name of a request that the server did not know was dropped from the list (`filter_map`), so the answers of the other names moved to the
  wrong positions. This affected the AA-specific `IM_Transfer_Set` once it became a name the model answers to. Each name now has its own answer.
- The module documentation of the server still said that the devices were not served. Corrected.

## Not done, and why

- **Real execution of a command.** A device's command completes at once in the model; the application has no hook to execute it and report
  the outcome (503 §7.2.6.3.3 waits for the device). Recorded in D-066.
- **The device actions as MMS event conditions** (`<device>_time`, `_reset`, `_success`, `_fail`): the stack serves no event conditions.
- **A Local Reset from the application**: the `Device::local_reset` of the link is not exposed by the server.
- **The critical acknowledgement** and **GetNameList**, as before (D-046, D-049; the server's module documentation).
- **End-to-end tests of the bench**: they are C8, with the matrix.
